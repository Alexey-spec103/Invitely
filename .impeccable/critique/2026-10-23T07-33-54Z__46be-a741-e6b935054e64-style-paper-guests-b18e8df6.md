## Design Specificity Verdict

**Design-director read**: Style and Paper are genuinely wedding-specific — occasion-scoped theme filtering, printable-media rail (envelope/program/save-the-date), QR-linked personalized invitations, card-flip previews. Guests, by contrast, reads like a generic CRM contact list with wedding vocabulary layered on top (RSVP badges, paper/site toggles) rather than something emotionally tuned to "who's coming to my wedding" — the highest-stakes recurring question a host returns to this tab to answer. Specificity ranks Style > Paper > Guests, with Guests the one surface closest to "could be any SaaS admin list."

**Deterministic scan**: `impeccable detect --json` returned a clean exit 0 (`[]`) on all three tabs' source directories — zero structural/anti-pattern findings, a genuinely clean technical baseline. A hue scan for ungrounded "AI-teal" accents found zero systemic hits; the only teal-range matches were a conventional green "no payment collected" success badge, correctly identified as intentional, not templated.

**Live contrast scan** (the hard evidence this run adds beyond the Site critique): 71 flagged nodes / 22 root causes on Style, 16 / 7 on Paper, 31 / 9 on Guests. The two largest, cross-tab root causes:
- **Brand orange as text on white** (`#ff6b45` / `--dash-accent`, 9 nodes across all three tabs, 2.48–2.82:1) — the codebase already defines a fixed, AA-compliant variant (`--dash-accent-text: #c2410c`, documented in `app/globals.css` as the fix for exactly this problem) and uses it correctly in `.dash-btn-primary`/`.landing-cta`, but `grep` shows **30 files** under `app/dashboard` still reference the raw, unfixed token directly.
- **Bottom progress-stepper labels** (Paper + Guests, 11 nodes) — as low as **1.04:1**, visually confirmed via zoomed screenshot as barely distinguishable pale-gray-on-light-lavender text. The single most severe confirmed defect in this run.

## Overall Impression

Style and Paper carry real product character — this isn't a reskinned generic dashboard. The biggest opportunity is two-sided: first, a confirmed, cross-tab, already-half-fixed accessibility gap (roll the proven `--dash-accent-text` token out to the 30 files still using the raw unreadable one — this is measured, not a judgment call, and the fix pattern already exists and works). Second, two real code bugs in Style's newer "design slots" feature silently undercut the product's own occasion-curation logic: a host adding a candidate theme sees all 124 themes unfiltered (including Corporate/Birthday-only styles), and the color-variant swatch picker is architecturally unreachable for the product's primary event type (weddings) because it's gated to theme categories (`modern`/`minimal`) that the wedding occasion filter excludes outright.

## What's Working

1. **Paper's locked-download modal** ("Continue with watermark anyway") — surfaces the paywall at the moment of commitment instead of silently watermarking a download the host didn't expect, while still respecting their right to proceed. Textbook error prevention.
2. **Guest removal's optimistic-hide + delayed-commit undo** (5-second toast, restores hidden rows if the delayed delete fails) — a well-engineered safety net given the schema has no soft-delete column.
3. **Occasion-scoped theme filtering on the main Style gallery** — a Wedding host never sees Corporate/Kids-Party-only categories cluttering their search. Well-reasoned and (per its own code comments) already validated against a prior live bug. The irony: this same logic doesn't reach the "Add a design slot" modal — see Priority Issues.

## Priority Issues

**[P1] Systemic contrast failures on brand-orange text/backgrounds, confirmed cross-tab, fix already exists**
Why it matters: `--dash-accent` (#ff6b45) used directly as text-on-white or white-on-background reads at 2.48–2.82:1 — well under the 4.5:1 AA floor — on the "Wedding" chip, "Front"/"Back" tabs, notification badges, and quick-links across Style, Paper, and Guests. The bottom stepper compounds this down to 1.04:1 in places. This is the same class of bug already found and fixed once this session on the Site tab's Editable Blocks panel.
Fix: `app/globals.css` already defines `--dash-accent-text: #c2410c` for exactly this case, proven in `.dash-btn-primary`. Sweep the 30 files still using the raw `var(--dash-accent)` as a text/foreground color and switch them to the accessible token; fix the bottom-stepper's two label colors directly.
Suggested command: `/impeccable audit` (or a direct accessibility sweep) + `/impeccable harden`

**[P1] "Add a design slot" modal bypasses the app's own occasion filtering**
Why it matters: `DesignSlotsPanel.tsx`'s gallery call omits `eventType`, so a host shortlisting a candidate theme for their Wedding sees all 124 themes unfiltered — including Corporate/Birthday/Kids-Party-only categories the main gallery deliberately hides — with no signal that a pick is off-occasion. It also omits `selectedId`, so the active theme isn't highlighted there either.
Fix: pass `eventType={eventType}` and `selectedId={currentThemeId}` into that `<ThemeGallery>` call, same as `ThemeSelectForm.tsx` already does one level up.
Suggested command: /impeccable harden

**[P1] ColorVariantPicker is architecturally unreachable for weddings**
Why it matters: the swatch picker only renders for `modern`/`minimal` category themes, but the Wedding occasion filter excludes both categories from the curated gallery entirely — a built, working feature that essentially no wedding host (the product's core audience) will ever see.
Fix: either extend the Wedding occasion filter to include a wedding-safe modern/minimal subset, or extend `colorVariantOptionsFor` to cover a category Wedding hosts actually reach (e.g. romantic/botanical siblings).
Suggested command: /impeccable harden

**[P2] No confirmation or quick-undo on direct theme selection**
Why it matters: clicking any gallery card instantly commits `updateTheme` with zero toast or safety net — the single highest-stakes, most emotionally loaded decision on this whole surface (it defines the entire event's look), with worse reversibility UX than deleting a guest already has.
Fix: reuse the guest-deletion pattern already built this session — a brief "Switched to {theme} · Undo" toast on direct gallery selection.
Suggested command: /impeccable polish

**[P2] Style tab's filter sidebar violates the ≤4-visible-options cognitive-load guideline**
Why it matters: the gallery entry row (Popular/New/Spring 2026/Winter 2026/Autumn 2026/Summer 2026/Favorites — 7 options) and the "OR PICK A SPECIFIC STYLE" category list (14–16 flat chips) are both visible simultaneously with no sub-grouping, on the page most likely to be a first-timer's very first dashboard screen.
Fix: collapse the category chips into 2–3 labeled groups (by technique/season/etc.), or progressively disclose beyond the first 4–6.
Suggested command: /impeccable layout

## Persona Red Flags

**Alex (Power User)**
- Style: re-opening "Add a design slot" forces a full re-search from scratch — its filter state is independent of (and unfiltered by) the main gallery he just used.
- Guests: bulk *delete* exists but bulk *modify* doesn't — a host managing 150 guests hits this asymmetry immediately.
- Paper: no keyboard shortcuts for undo/redo in any of the six canvas editors; undo/redo are button-only.

**Sam (Accessibility-Dependent User)**

- Cross-tab: the confirmed 1.04–2.82:1 contrast failures above directly fail Sam's 4.5:1 minimum on interface chrome she depends on.
